# ADR 索引与规范

ADR（Architecture Decision Record，架构决策记录）用于记录**会影响后续实现方式**的决定：为什么这样做、放弃了什么、代价是什么。产品需求变化写入 PRD，页面与交互细节写入 [DESIGN](../DESIGN.md)，版本变更写入 [CHANGELOG](../../CHANGELOG.md)。

## 何时需要写 ADR

- 引入或放弃技术选型（框架、构建工具、数据来源、部署方式）
- 改变项目结构、路由方案、状态管理方式
- 做出会影响多人协作的约定，且存在明显备选方案
- 推翻此前的 ADR（应新建一篇并标记取代关系，不直接改写历史）

不需要写 ADR：文案调整、样式微调、局部 bug 修复、假数据增删。

## 命名与格式

- 目录：`docs/adr/`
- 文件名：`NNNN-kebab-case-title.md`，四位递增编号，例如 `0004-migrate-to-uni-app.md`
- 状态：`提议` / `已接受` / `已废弃` / `被 ADR-000N 取代`
- 每篇固定章节：状态、日期、背景、决策、后果（正面 / 负面）、替代方案

## 模板

```markdown
# ADR-000N：决策标题

- 状态：提议
- 日期：YYYY-MM-DD
- 相关：PRD / DESIGN 链接

## 背景

要解决什么问题？有哪些约束（时间、技术栈、团队、合规）？

## 决策

一句话说明决定，随后列出关键做法。

## 后果

### 正面

### 负面 / 代价

## 替代方案

- 方案 A：为什么不用
- 方案 B：为什么不用
```
